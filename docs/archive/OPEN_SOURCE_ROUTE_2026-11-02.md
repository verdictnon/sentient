# Sentient: route to a working retail video system

Research and local execution: 2 November 2026. Scope: public data, one RTX 4050 Laptop with 6 GiB VRAM, two developers. This review distinguishes available code/weights from measured behavior in this project.

The direction is sound **if the first deliverable is recorded-video analytics plus reviewable interaction evidence**. The earlier training loop was too detached from that deliverable: a good score on annotation-centered, supplied-subject clips does not establish person discovery, continuous event proposals, counting, item state, or payment. A larger GPU does not remove those gaps.

The useful next milestone is a complete data path: original video → pretrained person detector → camera-local tracker → counts/dwell and label-free action proposals → actual action-model scores → seekable evidence → versioned human review → a validated, masked training manifest. That is what this work implements and exercises. See `ACTION_WORKER_MILESTONE.md` for the actual results and commands.

The Intel reference is particularly informative: its documented workloads use `person-detection-retail-0013`, a retail re-identification model, a pose filter, and Qwen2.5-VL-7B for selected evidence. It recommends at least 16 GB RAM and 32 GB for headroom. This is evidence for decomposing the problem and invoking expensive models selectively, not evidence that its model is more accurate on our camera. Sentient does not add face identification, watchlists or cross-camera identity as part of this milestone.

## Are our data and model choices appropriate?

**RetailAction is relevant but incomplete.** It supplies take/put/touch interactions and subject poses, but its clips contain at most 32 motion-selected frames and are strongly take-dominated. Its MP4 playback cadence does not establish physical event timing. Supplied subject crops simplify a problem that the tracker must solve on new video. More of the same dominant class cannot substitute for reliable return labels, visible item state, hard negatives and an independent evaluation set. [Publisher description](https://huggingface.co/datasets/standard-cognition/RetailAction).

**X3D is a cost baseline, not a proven best architecture.** We have tested a limited set of representations, repeatedly reused development data, and obtained no reliable recent gain. Replacing the model because another paper reports a larger number on AVA/Kinetics would be an invalid comparison. The current V5 checkpoint is usable as an uncalibrated review-ordering signal; the worker explicitly keeps its actions unknown. Its poor return performance remains unresolved.

**Add continuous data for a defined purpose.** The original MERL publisher describes 106 overhead shopping videos, roughly two minutes each, with reach/retract/inspection labels and research availability. This milestone downloads one 15.7 MB sequence from a pinned Voxel51 mirror and quarantines it as an external continuous diagnostic. Its provenance and hash are recorded. It is not folded into RetailAction training, and reach/retract are not silently renamed take/put. [Original MERL source](https://merl.com/research/highlights/merl-shopping-dataset), [mirror/files](https://huggingface.co/datasets/Voxel51/MERL_Shopping_Dataset/tree/main/data).

The MERL diagnostic is a controlled overhead shopping scene, not a crowded deployment store. Its source labels do not establish payment or theft. The original publisher's research-use terms and the mirror's stated noncommercial scope remain relevant. RetailAction also has custom attribution, deidentification and commercial terms; preserve that lineage rather than assuming model export removes it. [RetailAction license](https://huggingface.co/datasets/standard-cognition/RetailAction/blob/main/LICENSE).

## Local hardware versus Colab/cloud

The local RTX 4050 is sufficient for the inference/review milestone actually executed here. The 85-view/407-window sparse review run uses about 179 MiB peak **PyTorch allocated GPU memory**, not total device memory. That measurement is not a live multi-camera capacity estimate. Detector performance on the continuous clip is measured separately in the milestone report.

Use cloud GPUs when a frozen experimental protocol and memory/throughput measurement justify a specific larger run. No cloud platform or price comparison was needed or purchased for this milestone. Do not pay to repeat the same weak-label/head sweep faster. For future visual fine-tuning, preflight a tiny batch locally, measure peak VRAM and wall time, then decide whether a larger GPU buys a useful experiment. Model accuracy, inference latency, and simultaneous-camera capacity are separate measurements.

## Shipping gates after this milestone

1. Keep the partner's tracking acceptance status honest. A public continuous diagnostic adds evidence; it does not replace independent reference counts, missed-person checks and identity evaluation on the intended camera view.
2. Use the scored queue for actual human adjudication of a small group-balanced batch. Inspect subject correctness, item leaves/stays/returns, visibility and boundaries. Save revisions and declare human origin; do not accept model suggestions wholesale.
3. Treat all annotation-free worker output as triage until a continuous held-out set supports calibrated action thresholds. Track false review alerts per source-video hour, class/event recall, and abstention coverage separately.
4. Next model experiment: one bounded comparison using reviewed labels and either visual fine-tuning or manipulation-oriented pretraining. Freeze splits/protocol before examining a new check set. Additional touch-head/epoch sweeps are not the priority.
5. For product analytics, distinguish image-space occupancy from calibrated floor heatmaps, queue-area occupancy from verified service events, and checkout-area visits from payment. Finish one view before multi-camera association, RTSP and item/SKU inventory.

No research result here establishes automated theft detection or proves that any default model is globally best. The practical gain is replacing disconnected experiments with an executable, auditable integration path and measured failure cases.

## Follow-up from the actual overhead diagnostic

The generic detector produced tiny false boxes and overlapping person tracks on MERL. That is a concrete reason to keep detector quality separate from action-head quality. The integration adds optional, recorded size/NMS scene settings, disabled by default, and tests one explicit configuration on the same diagnostic. It is an engineering comparison on an inspected clip, not an independent accuracy gain.

More appropriate detector data/model leads now include [WEPDTOF](https://vip.bu.edu/projects/vsns/cossy/datasets/wepdtof/) and its [publisher download terms](https://vip.bu.edu/projects/vsns/cossy/datasets/wepdtof/download/), [LOAF's official implementation](https://github.com/BUPT-PRIV/LOAF/blob/main/README.MD), and [RAPiD-T's official code/weight links](https://github.com/ozantezcan/RAPiD-T). They target overhead/fisheye detection rather than generic action classification. RAPiD-T documents an older PyTorch 1.9 runtime and noncommercial use; LOAF's paper describes NC-SA data terms. WEPDTOF's publisher wording combines a noncommercial restriction with a CC BY 4.0 reference, so treat commercial scope as unresolved. None was installed, benchmarked, or granted commercial approval here. Rotated boxes would also need an explicit adapter to our original-coordinate xyxy contract. These are focused follow-up candidates if overhead detection remains the next measured bottleneck, rather than another unfocused action-model sweep.
